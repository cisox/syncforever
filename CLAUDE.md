# Sync Forever (syncforever)

Host code lives in `host/` (uv project, Python ≥3.11): `cd host && uv run pytest`, `uv run ruff check . && uv run ruff format .`. CLI is `sfe` (alias `syncforever`); `uv run sfe --sim DIR …` runs against the fake cart.

The Sync Forever NES and SNES apps share `app/` (cc65; `app.c` the screens' logic, `link.c` the protocol, `clock.c`), so change them there; each console's `src/` has only its screen, `plat.c` (start, exit), `plat_config.h` and `link_io` (how bytes travel). There's no SNES emulator: `nesemu` covers the shared logic, and only `snes/src/` needs the console alone. The NES app lives in `nes/`: `cd nes && make`, `make install` (put + launch on the cart, menu must be up), `make package` (the copy the box ships, `host/src/syncforever/data/`; a test fails when it's stale). Its font is read at build time from the user's `nesos.nes` backup (Krikzz's artwork; never commit it); the shipped copy has edio's MIT font and the box patches each cart's own font in (`apps.py`, `chr.py`). No usable emulator on this Mac (Mesen 2 and Homebrew FCEUX both failed). Instead `syncforever.nesemu` (py65) runs the ROM headless: screen text, highlight, PNG screenshots, a fake EverDrive FIFO, and `violations` for VRAM writes outside vblank; `tests/test_app.py` builds the ROM via `make -C nes` and drives it. Its `$2002` read fast-forwards to vblank, valid only because the app reads `$2002` solely to wait. Colours, timing feel and flicker still need the cart. End-to-end tests (`tests/test_app.py` `Session`) wire `FakeN8Pro.on_start` to boot the app in `nesemu`, so `AppServer` talks to it through `N8Pro` exactly as on hardware; `sfe serve` (`box.py`) runs the same server on the real port. The Genesis and SNES apps are `md/` and `snes/` (same `make`, `make install`, `make package`; the SNES's `make install` doesn't launch); the N64 app is `n64/` (below).

`docs/design.md` is the agreed product direction (a box on a Raspberry Pi, an app on each console for sync).

## Keeping the docs current

A change isn't done until the docs match, in the same commit. Check what it touches: `README.md` (cart status, features), `deploy/README.md` and `deploy/config.example.toml` (install, settings), `docs/app-protocol.md` (messages), the cart's plan or protocol doc (`docs/snes-plan.md`, `docs/n64-plan.md`, `docs/x7-protocol.md`, `docs/usb-protocol.md`), `docs/cartridge-compatibility.md` (carts), `docs/safety.md` (guards), and the landmines below. Say "working on hardware" only for what has run on the cart; say what's only been tested in an emulator or simulator. A NAS is optional, so say "library" and "save folder", not "NAS". Keep dated findings and mark them superseded rather than rewriting them. Dropped plans and features go in `INTERNAL.md` (gitignored), never in public files.

## Landmines

- **Never send a partial `F_FWR` payload.** The cart consumes the declared length as data no matter what follows, and only a power cycle recovers it. Keep `N8Pro.write`'s Ctrl-C/SIGTERM deferral and wedge tracking intact. `sfe serve` serves each cart in its own thread, and signals reach only the main thread, so a stop must go through `n8pro.stop_writes()` (cli `_finish_writes`) before the process exits: daemon threads die mid-payload otherwise.
- **Open cart ports only through `transport.open_port` (exclusive flock).** The box service and a manual `sfe` both talking to one cart mix their bytes (a PRO cart can wedge mid-write). With the service holding a cart, `sfe` run as root stops it for the command and starts it again (`cli.main`).
- **Never use `mem_wr` with exec `0xAA` or `CMD_HARD_RESET (0x12)`** on this cart; both wedge it (NESCD). Writes to PRG/SRM PSRAM crash a running program.
- **Relaunching our app needs a menu that's finished booting.** N8: first ping 4.5 s after RESTART (2.25 s after the app exits), launch 2.0 s after the first answer (1.5 + 0.3 gave Error:40 once, 2026-11-02). Mega: `EverDrive.reset_to_menu` (host reset `0x29`, config reset, release; the menu sends `r`), never pings into its boot (Error:2A/40, 2026-11-02). While a relaunch is pending the box does nothing else with the cart (`box.py`).
- `F_DIR_GET` maximum is 32 entries per call.
- **The menu caches its folder, and USB changes to it break the menu.** (1) `F_DIR_LD` over USB replaces the menu's loaded directory (one shared MCU slot); `N8Pro.list_dir` therefore reads the snapshot first (`read_snapshot`, no load), then finds that folder and reloads it with options `0x03` (sorted + hide system, what the menu uses). Keep that, and route every host `F_DIR_LD` through it, or the next snapshot read lies. (2) The menu reads names from the MCU's snapshot as it pages but keeps its own entry count from its own load. A snapshot smaller than that count breaks it (e.g. deleting a snapshotted entry); refreshing the snapshot (`F_DIR_LD` with `0x03`) to the same count shows changes exactly, a larger count just hides the last entries. Both show `Error:81` (`ERR_OUT_OF_DIR`) on the next scroll. Single file reads/stats/opens are fine.
- Menu commands go through the FIFO like the ping: `*n` + string (path **without** a leading slash) → u8 status + u16 mapper, then `*s` starts it (`N8Pro.menu_install`/`menu_start`, `ops.launch`).
- **Don't call edio's `ed_exit_game()` from ROM code.** Writing `map_idx=255` swaps the menu's ROM in immediately, so the rest of the function vanishes: hang, and the in-game reset stops working until a power cycle. Use `exit_to_menu()` (`nes/src/fast.s`), which sends the config from zero page.
- **cc65 (2.18 here, `-O`) miscompiles `p[i++]` when `p` is a constant address (`((vu8 *)0xF000)[i++]`): it increments `i` before indexing**, so every access is one byte off (the SNES app ate each WELCOME without its 'S'; the simulator test's own ring writes did the same). Read or write, then `++i` on its own line. `make -C snes test` runs `app/link.c` with `snes/src/link_io.c` in `sim65`.
- **cc65 2.19 `-O` miscompiles `a[x < y ? x : y]` with `y` a parameter** (it read another stack slot: long names cut to 3-4 letters). Clamp with an `if` first; check `build/*.s` when a C expression misbehaves only at its edge.
- **X7 (N64) ROM code: access the cart's registers (`0x1F800000+`) only by 4-byte PI DMA, never CPU loads/stores.** libdragon's `usb_write` uses `io_read`/`io_write`; streaming a few blocks back to back with it froze the N64 on the PI bus (no timeout can fire; power cycle only, the X7 has no in-game reset). Krikzz's menu uses DMA only (disassembled); `n64/poc/poc.c` `reg_wr`/`reg_rd`/`tx_frame` do the same and stream cleanly (2026-11-02). The app is `n64/` (`make` runs in Docker, image `sfe-libdragon:preview`, see `docs/n64-plan.md`; `make package`), its protocol `docs/x7-protocol.md`, the box side `x7.py` (`sfe --x7`), the fake `x7sim.py`. No test checks the packaged `.z64` is current (building needs Docker).
- **Genesis builds (m68k-elf-gcc 16, Homebrew): compile Krikzz's `edio` with `-fno-reorder-functions -fno-toplevel-reorder`, and link `sega.o` first.** `ed_init` copies `ed_halt_app` to RAM with length `ed_halt_app_end - ed_halt_app`; GCC 16 reordered them, the length came out -2 (65534 bytes), the copy wiped RAM and the stack, and the cart showed Krikzz's magenta crash screen (his exception handler paints colour 0 `0x0F0F`). Fixed and verified on the Mega 2026-11-01.
- **NES palette writes early in a vblank don't all stick on hardware** (rendering on): entry 2 written ~70 cycles in kept its old colour while entries 14-15 changed; nesemu passed regardless (2026-11-02, cause unknown). `scr_queue_pal` therefore queues the palette twice in one vblank (the second copy lands whole); nesemu models the loss (`PAL_SETTLE`), so a single upload fails the firmware colour tests. Don't "optimise" it back to one slot.
- NES app: vblank (polled, no NMI) fits 3 queued rows via the asm `scr_vblank_push`; a C byte loop overruns even 2 and scatters garbage tiles. Page changes draw into the hidden nametable and flip (`scr_queue_back`/`scr_flip`); `scr_off()`/`scr_on()` blanks a frame. `scr_queue_row` returns 0 when the queue is full (the palette takes 2 of the 3 slots) and that row is simply lost: the status and detail rows are queued from the main loop by dirty flags and retried.
- App protocol (`docs/app-protocol.md`): while our app runs, the serial port carries only app frames and our FIFO writes; host file commands then work (verified). **Launching right as the menu comes back from our app shows Error:40/48/2A**: `appserver.MENU_FIRST_PING`/`MENU_SETTLE` (4.5 s after RESTART, then 2.0 s after the first answer) are hardware-tuned; the app's self-restart after an update uses them. Without a box talking to it the cart drops off USB (~0.2 s) at each menu↔program switch, killing open handles; `box.py` reopens.
- **An app's HELLO lands in the middle of a host read on the N8 and Mega** ("read: 0x53": the `S` of its frame, 2026-11-04). The apps give up on a silent box after 30 s, so anything long must keep them informed: `make_plan`'s `keep_alive` and the save backup's STATUS (at most every `romsync.STATUS_EVERY`, 2 s), and `expect` on STATUS for a copy or move (the Genesis and NES apps wait twice that plus 30 s).
- The save store is append-only and holds only what carts held. Other programs may read it but never write to it: a version someone else added would look older or newer than the cart's and get buried by the next backup. The box never writes saves to a cart.
- ROM sync (`romsync.py`) touches ROM files only and never a cart's system folder (`EDN8/`, `MEGA/`, `ED64/`, `sd2snes/`: `guard`); Mirror deletes only manifest-"owned" files. Plans list the cart with `list_dir(restore=None)` because they run while our app is up (the menu reloads on return); don't reuse that outside an app session.
- Save backups (`saves.py`): versions are ordered by the leading sequence number, never by name or clock; never overwrite a backup file (`open(..., "xb")`).
- **Never send menu command `*r` (reboot)** on this firmware: the menu acks `00`, then the console goes black until reset (twice, healthy and errored menu). edlink's `reset` does exactly this.
- **Don't talk to a menu that may be in use.** Pings (FIFO writes) are read as the menu's own MCU replies: Error:40/2A. Opening a file closes the menu's (one file object, shared): Error:09 `FR_INVALID_OBJECT`, and could corrupt a save the menu is writing. Only `F_FINFO` (stat) proved safe (716 during heavy use). Open files only while a game or our app runs (both verified), and in someone else's game only read: writes there were never tried. Mirror and strict must never treat a missing or empty library as "nothing to keep" (an unmounted disk or share is an empty folder: `make_plan`, `run_plan`, `AppServer._watch_library`). `docs/test-results.md` 2026-11-01.
- **STATUS is the sticky result of the last command, not a menu/game flag** (verified on hardware). Never gate on it. The write gate is `N8Pro.menu_ping()`: only the ROM-select menu answers `*t` with `k`.
- The N8 PRO enumerated as `0483:5740` (ST VCP) until firmware v25.1123, then `38DF:0017` ("EverDrive N8", KRIKZZ-IT; macOS asked to allow the accessory again); the Mega likewise. SYS_INF kept the plain edio layout (`device_id` @46) and **its build date (2025-09-30 16:36) and mcu 1.03 did not change with the update**, unlike the Mega's: which firmware a cart runs comes from comparing its menu file with the .efu (`firmware.py`), the date only on the Mega.
- The cart's clock is wrong (writes stamped months off), so never use cart mtimes for sync decisions; use size and SHA-256.
- `sim.py` encodes our *beliefs* about the cart. Lines marked `SIM ASSUMPTION` are guesses, so a passing sim test is not evidence for them. When hardware disagrees, fix the sim first, then the client.
- ThroatyMumbo/NESPC (`edn8.py`) is GPL-3.0: read it for facts, never copy code. Edlink's device/link C# sources are not published (absent from krikzz/edlink despite the csproj).
- **FXPAK PRO (SNES): never send GET for a file that isn't there, and never cut a GET short.** Firmware 1.11.2: a missing file's GET answers error 4 with the previous file's size and then hangs the MCU's USB; an aborted GET (DTR drop) leaves the MCU's read position, so the next GET is shifted, and one shifted past its file's end hangs USB the same way (power cycle only). LS has no sizes on 1.11.2, so a size costs reading the whole file (`fxpak.py`, `docs/snes-plan.md`). **Names on the wire are Windows-1252, not UTF-8** (the firmware's FatFs is code page 1252, no Unicode): a UTF-8 path for a name with "é" gets FR_NO_FILE; names outside 1252 can't be stored, so sync skips them. **Keep PUT data paced** (`FxPak.block_gap`: flush, then 1 ms after each 512-byte block): sent back to back, uploads stall the cart's USB for good (power cycle only; SNES reset doesn't help), 40/40 clean paced (2026-11-03). The SNES app (`snes/`, cc65 6502 code in emulation mode) talks to the box through two rings in cart memory (`fxapp.py`, `snes/src/link_io.c`): **write SNES space only while INFO says our app runs** (at the menu, address 0 is the menu's ROM). **No PUT may meet the cart's autosave**: while a ROM runs, the firmware writes save RAM to its .srm ~1.3–3 s after it changes, and PUT data (file or SNES space) is handled in the USB interrupt, so one landing during that save hangs USB until a power cycle (uploads stalled with the app up, 20/20 clean at the menu, 2026-11-03). Our app's ring is in save RAM, so `FxApp._quiet` gates every PUT; don't write to the cart around it while a ROM runs. For the same reason the app never writes save RAM on its own during a sync (no timeout, no HELLO): one MSU-1 track can be a 30-minute PUT (`msu.py`). **Save RAM persists** (the cart reloads `Sync Forever.srm` at start): until the app sets up, the last session's messages are in its ring, so `FxApp` starts reading at the head it first sees; reading from the ROM's ack replayed an old SYNC_RUN (a strict sync nobody pressed, 2026-11-03). **Uploads can start slowly**: FatFs (R0.11, FAT32 only, no exFAT) looks for free space from the last file it overwrote, inside the USB interrupt; with the app's `.srm` (rewritten by every autosave) behind 46 GB a computer copied on, each new file took ~11 s to start (2026-11-04), more than the old 10 s write timeout. `fxpak.WRITE_TIMEOUT` is 120 s, and `FxApp.after_first_copy` deletes the `.srm` once per sync so the cart recreates it at the free space. MENU_RESET (the app's B) and BOOT (restart after an update) are the only console commands the box sends, with the owner's go-ahead (2026-11-03); never RESET or POWER_CYCLE.
